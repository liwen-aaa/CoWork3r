# 纪律（disciplines）

> 本文件是**判据集合**，不是说明文档。每条给出：判据（怎么判断违反了）＋ 落点（在哪被强制）。
> 落点为「规约」= 只写在文本里，**接受它会被跳过**（见 D-02）；落点为路径 = 有机制。
> 只增不改：旧条目正文不动，修订另起一条并标注取代关系。
>
> 与老仓库的关系：`work-flow`（留档）的 `docs/run/hard-won-constraints.md` 30 条尚未迁移，
> 迁移后落在 `docs/constitution.md`，编号 A1–F3 保持不变。本文件只放**架构层纪律**——
> 决定形状的那几条，以及本轮讨论新增的。两者不重复：宪法管「实现别重踩坑」，本文件管「东西长成什么样」。

## 一、形状（violating these = 换了一个东西）

| id | 纪律 | 判据 | 落点 |
|---|---|---|---|
| D-01 | **生产者不能宣布自己完成** | 判定「完成」的一方，其产出不被自己评判 | dev / tester 上下文隔离（架构） |
| D-02 | **纪律不进拦截链就不会被遵守** | 任何「必须写 X」的要求，要么在 `tool_call` 里 `block`，要么显式承认会被跳过 | 各 gate；本表「落点」列 |
| D-03 | **可推导的值不让人填** | 存在两处必须字符级一致、由人手写的值 = 违反 | 配置单点（03-config） |
| D-04 | **一概念一权威文件** | 同一规则写全在两处 = 违反；其余只链不复述 | 评审时人查 |
| D-05 | **散文里不留第四类** | 为什么 → `decisions.md` 一行；是什么 → 接口文件；必须恒成立 → 测试。三者之外不写散文 | 评审时人查 |
| D-06 | **架构文档是脚手架，不是建筑** | `docs/modules/*.md` 在对应代码落地后必须收缩：职责 + 不负责什么 → 模块目录的文件头注释；设计点 → 测试名；取舍理由 → `decisions.md` 一行。只留 `modules/README.md` 的依赖图。**代码已落地而文档未收缩 = 两份权威（D-04）** | 验收时人查；模块完工即检 |

## 二、决策与规划

| id | 纪律 | 判据 | 落点 |
|---|---|---|---|
| D-10 | **能不能精确陈述，不是能不能回答** | 问题已能精确陈述 → 进未决表（哪怕答不了）；陈述不清 → 留散文，**不许预先切成条目** | 澄清规约 |
| D-11 | **想直接动手了 = 该交棒了** | 澄清/规划会话里开始写生产代码，即为越界信号 | 澄清规约 |
| D-12 | **决策记录只在实现之后写** | `decisions.md` 不得记录尚未落地的决定 | 澄清规约 + 评审 |
| D-13 | **写记录的双条件** | 同时满足：有人真主张过一个具体替代方案 ＋ 否决理由读代码看不出来。不满足则降级为测试名 / 注释 / 不写 | 评审时人查 |
| D-14 | **已 PASS 的里程碑节冻结** | 回头修改已验收里程碑的断言或结论 = 伪造记录 | 规约（拟机制化，见未决） |
| D-15 | **断言节只有人能改** | arch 可改状态标记、未决表、风险节；不得改断言。arch 认为断言错了 → 往「风险与未决」写清该怎么改 + `escalation` 升级给人，由人改（多一次往返，换「断言源不被产出链修改」） | 规约（拟机制化，见未决） |
| D-18 | **规约可追加不可替换** | 项目侧只能追加一段说明（`roleNotes`），不得覆盖角色规约本体——否则 tester 可被换成橡皮图章（D-01 的形状） | 03-config 字段表 |
| D-16 | **规划书要能塌缩** | 最小合法形态 = 一个里程碑 + 一条断言 + 未决表「无」。模板撑不住这个塌缩即为超重 | 04-plan 解析器 |
| D-17 | **归档不进每轮读序** | 任何规约里出现「每轮读 `decisions.md`」= 违反（归档变成了每轮成本） | 06-roles 评审 |

## 三、断言与验证

| id | 纪律 | 判据 | 落点 |
|---|---|---|---|
| D-20 | **`[auto]` / `[human]` 二分** | 每条断言必须标其一；`[auto]` 须含命令或路径，`[human]` 不得为空 | 04-plan 解析器 + gate |
| D-21 | **`[human]` 是人的原话** | 人工关卡只问 `[human]` 条目；它应在澄清阶段由人说出，不由 AI 归纳 | 澄清规约（无法检查，接受稀释） |
| D-22 | **仪式量从断言表推导** | 产出文件要求 = 每条断言一行结论。固定小节数 = 违反（小改动会被迫凑格式） | 05-gates |
| D-23 | **无自动化基建时显式降级** | 项目无法自动测 → 必须显式声明该 gate 为空，不得静默降级 | 03-config 诊断 |
| D-24 | **逐条签字** | 规划书写盘前，断言逐条过人；整份「你看一下」不算签字 | 澄清规约 |

## 四、外部化与不自造

| id | 纪律 | 判据 | 落点 |
|---|---|---|---|
| D-30 | **载体必须在视线路径上** | 需要人主动去打开才能看见的待办 = 无效载体。未决/待回状态必须出现在 `/status` 与启动简报里 | 01-channel + 07-adapter |
| D-31 | **成熟方案优先** | 需要工具/机制时先查现成方案（pi 原生能力、issue tracker、npm 包），有可用的直接用 | 评审时人查 |
| D-32 | **环境即边界** | 编译/工具链/环境错误不循环尝试：记录 + 报告，最多试 1 次替代 | 角色规约 |
| D-33 | **开窗口由人执行** | 不在 agent 会话内开窗口 / 浏览器 / IDE。无例外 | 角色规约 |
| D-34 | **物理删除归人** | AI 可提议删除并给出依据，不执行 | 角色规约 |

## 五、机制增殖（本项目的死因）

| id | 纪律 | 判据 | 落点 |
|---|---|---|---|
| D-40 | **新机制的双问** | ①有没有被观察到的失败模式？②它保护用户能力，还是保护本仓库的自证？后者需额外理由 | 评审时人查 |
| D-41 | **自检不得超过运行时** | 测试代码行数 > 运行时代码行数 = 红线，需停下来审 | 定期人查 |
| D-42 | **升级由不够用触发** | 未决表 → 依赖拓扑 → 独立票系统，每级由一次真实的「装不下了」推上去，不由预判 | 评审时人查 |
| D-43 | **超预算先砍功能** | 接入成本超预算时，优先砍功能或加默认值，其次才改文档 | 08-分发 |
