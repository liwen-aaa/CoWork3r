| 2026-08-24 | 三个独立 pi 进程 + 磁盘文件消息通道，人随时能介入任一窗口 | RPC 编排器 / 单进程编排（pi 原生支持，1576 行文档；Node 应用还能直接 import AgentSession） | 人工介入是**主路径**不是异常路径（引入人工是为了省 token，人在环里是设定）；三个真窗口是可观察可介入的最小形态，RPC 编排器自动化但杀掉人工介入——要人工介入就得自建 UI，那是十倍预算。M6.6 判 FAIL 那天，抓到「唤醒从未接线」的不是任何测试，是人坐在窗口前看着它不动。读代码看不出这层：代码里只有 fs.watch，没有一个字说明为什么不用 RPC（08-21 聊天记录里的「零网络零中间件」记错了理由——RPC 也没有网络和中间件，它甚至更省） |
| 2026-08-24 | 单槽位收件箱是锁：每方向同时一条，禁止覆盖 | 互斥量 / 消息队列 / 目录+序号（D-42 的升级路径，触发条件未到） | 真实顺序是「懒得搞原型锁 → 恰好 work → 事后被论证成设计」；单槽位的并发源（同一方向同时一条）天然串行，换来零基础设施、状态一眼可见。升级方向已定未落地：`writeTextAtomic` 改 O_EXCL 原子创建，文件名即锁，跨进程安全（三个窗口是三个进程，「检查+写」分离有竞态窗口）。物化在 consensus.md #4。读代码看不出：inbox.ts 写的「实际流转里每个方向同一时刻只有一条在飞」是事后论证，不是设计起点 |
| 2026-08-24 | 协作状态存自造 state.json，不加锁 | pi 原生 appendEntry / sessionManager（extensions.md 的 State Management 一节） | 状态必须三窗口共享：milestone 由 arch 写、round 由 tester 写、双方互读。pi 的 session 是**单窗口**的，appendEntry 存进各自窗口的 session，互不可见——原生做不到跨窗口共享，自造 json + 原子写是唯一满足的形态。不加锁：并发源被单槽位锁串行化（fix_request 只有 tester 发），跨方向竞态（arch 开新里程碑 vs tester 处理旧 fix_request）落在里程碑切换语义下无害。写者归属表待补进 state.ts 文件头。读代码看不出：state.json 的存废与 pi 能力的关系 |
| 2026-08-20 | 相对 import 一律带 `.ts` 扩展名，目录 import 写到 `index.ts`；`moduleResolution: nodenext` | 无扩展名 + `moduleResolution: bundler`（原写法） | 目标形态里**没有打包器**：pi 用 jiti 直接加载源码，人工验证脚本用裸 node 跑，两者都要求精确到文件。`bundler` 的含义是「假定有打包器帮你解析」，而那个前提我们没有——M1 的人工验证第一次用裸 node 跑就撞 `ERR_MODULE_NOT_FOUND`。老仓库是唯一在 pi 里真跑起来过的形态，它的 import 全带 `.ts`。读代码看不出这一层：无扩展名写法在 vitest 里完全正常 |
| 2026-08-20 | PASS / FAIL 拆成两个 type（`verdict_pass` / `fix_request`），不做一个 type 的参数 | 老仓库的 `verdict` 参数写法 | 一个 type 两个目标地址（PASS→human、FAIL→dev），路由就只能在代码里 `if` 分流——而「代码里分流」正是那个 bug 的栖息地。拆开后每个 type 方向唯一，`to` 能由表决定。读 `ROUTES` 只看到九条并列，看不出为什么不合并 |
