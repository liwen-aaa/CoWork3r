# 决策记录

> 追加式，一行一条：日期 / 定了什么 / 否决了什么 / 一句理由。**只增不改。**
>
> 准入门槛是 D-13 的双条件，两条同时成立才写：
> ① 这个决定被真实地争论过（存在一个具体的、有人认真主张过的替代方案）
> ② 否决它的理由**不在代码里**（读代码看不出为什么不用那条路）
>
> 不满足就降级：测试名能表达的写测试名，一句注释能表达的写注释，什么都不用的什么都不写。
> 按 D-12，只在实现之后写——所以这里不会出现「计划要做什么」。
> 无预设起点：M1 三条取舍逐条筛完全部不够格，所以第一行来自 M1 的一次真实失败。

> 本文件**不进任何角色的每轮读序**（D-17）。它是归档，用途是三个月后有人问「为什么不用 X」时查得到。

| 日期 | 定了什么 | 否决了 | 理由 |
|---|---|---|---|
| 2026-08-20 | 相对 import 一律带 `.ts` 扩展名，目录 import 写到 `index.ts`；`moduleResolution: nodenext` | 无扩展名 + `moduleResolution: bundler`（原写法） | 目标形态里**没有打包器**：pi 用 jiti 直接加载源码，人工验证脚本用裸 node 跑，两者都要求精确到文件。`bundler` 的含义是「假定有打包器帮你解析」，而那个前提我们没有——M1 的人工验证第一次用裸 node 跑就撞 `ERR_MODULE_NOT_FOUND`。老仓库是唯一在 pi 里真跑起来过的形态，它的 import 全带 `.ts`。读代码看不出这一层：无扩展名写法在 vitest 里完全正常 |
| 2026-08-20 | PASS / FAIL 拆成两个 type（`verdict_pass` / `fix_request`），不做一个 type 的参数 | 老仓库的 `verdict` 参数写法 | 一个 type 两个目标地址（PASS→human、FAIL→dev），路由就只能在代码里 `if` 分流——而「代码里分流」正是那个 bug 的栖息地。拆开后每个 type 方向唯一，`to` 能由表决定。读 `ROUTES` 只看到九条并列，看不出为什么不合并 |
| 2026-08-20 | 角色规约不走 pi skill 机制，由扩展按 `WF_ROLE` 读一份 md 注入 system prompt | 三份 `SKILL.md`（老仓库的做法，也是 pi 的官方分发形态） | 三个理由叠加，读代码只看得出第一个：① skill 是渐进披露，全文靠模型自己去 `read`，而规约必须常驻；② 三份 skill 在三个窗口都可发现，dev 看得见 tester 的规约，D-01 的隔离就没了；③ 老仓库 `--skill` 路径与目录名两处必须字符级一致，`paper-arch` vs `paper-architect` 差三字母导致扩展静默失活。第②条是决定性的——它不是「skill 不好用」，是语义不匹配。读 `inject.ts` 只看到「读一份文件」，看不出为什么不用现成机制（D-31 要求优先用成熟方案，这里是有理由的例外） |
| 2026-08-20 | `roleNotes` 是一段，不按角色分三段 | 三段（`archNotes` / `devNotes` / `testerNotes`），接入项目更灵活 | 分三段会诱导人往里写角色行为，而角色行为不该由项目定义。项目该说的是「关于这个 repo 你要知道什么」，那对三个角色是同一件事。灵活性在这里是缺陷不是优点：它给了「把 tester 调软」一个官方入口（D-18 的形状）。字段表上只是一个 `roleNotes?: string`，看不出曾有过三段的方案 |
