# M1 人工验证凭证

> 命令：`npm run verify:m1` ｜ 执行者：人（物理终端）｜ 日期：2026-08-20

## 断言原文

> [human] 拔掉 `fs.watch` 后，在真实 pi 进程的窗口里投一条消息，不碰键盘，等它被轮询处理（≥10s）。
> 日志里要有明确的轮询触发标记，不是 mock 定时器凑出来的 —— C1 验函数行为，
> 这条验真实事件循环里 `setInterval` 没被饿死

## 实测输出

```
[0.0s] 监听已启动（fs.watch = 已禁用，轮询周期 = 10s）
[0.0s] 已投递 task_assignment → 收件箱（此刻起不要碰键盘，等约 10 秒）
[10.0s] ✅ 唤醒来源 = poll
[10.0s] 收到 M1 task_assignment

判定：PASS（轮询兜底在真实进程里生效，耗时 10.0 秒）
```

## 三条判据

| 判据 | 实测 |
|---|---|
| 唤醒来源是 `poll`（非 event / catchup） | ✅ 标记明文打印 |
| 耗时 ≥ 9.5s（真的等了一个轮询周期） | ✅ 10.0s |
| 30s 内有反应（`setInterval` 在真实进程里跑起来了） | ✅ |

## 这条断言抓到了什么

它不是走形式。第一次执行时立刻失败——`ERR_MODULE_NOT_FOUND`：`src/` 的相对 import
无扩展名，vitest 能解析（bundler 式），裸 node 不能。

顺着查出根因是 `moduleResolution: "bundler"`，而那个设置的含义是「假定有打包器帮你解析」，
可目标形态里没有打包器（pi 用 jiti 直接加载源码）。也就是说**整个 `src/` 此前只在 vitest 里能跑**。

若无此条断言，这个假设会一路带到 M6，在真开窗口那天暴露——那时要改的文件是现在的三倍，
且混在「三窗口跑不通」这个更大的问题里，归因会很难。

修复见 `docs/decisions.md` 第一行。
