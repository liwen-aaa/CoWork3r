只有真进程能看到「模型实际收到什么」。

（对话原文见当日会话记录，含模型自述工具表。）

dev 窗口 send_task 工具面无 arch 投递目标。依据：

## 断言二：M6.6 在新建空项目里真开三个窗口，跑通一个里程碑

### 断言原文

> [human] 在一个新建空项目里真开三个窗口，跑通一个里程碑 —— 这是唯一能证明
> 「它真的在运行」的事，mock-pi 永远证明不了

### 为什么这条必须留人工

E1 用同进程 mock-pi 驱动三个适配器，验的是**接线正确**。它不验 pi 的真实行为：
事件时序、`sendUserMessage` 语义、系统提示注入链。mock-pi 永远证明不了「它真的在运行」。

### 前置（已就绪）

- launch 脚本（`cb19801`）：trio.ps1 + 三个 bat，纯 ASCII、防重、wt 三竖排
- 包定义（`0b637d1`）：pi.extensions 指向真实扩展
- wire 接 schema（`e5479f6`）：send_task 工具面按角色生成
- 扩展可被 pi 加载（真进程已验证，见断言一）

### 执行步骤

1. 新建空项目：`mkdir wf-manual && cd wf-manual && npm init -y && mkdir src docs wf`
2. 拷 `templates/plan.minimal.md` → `docs/plan.md`，拷 `templates/wf.config.json` → 根目录，
   把 `"test"` 改成 `null`、删掉 `"gate"`（空项目没有 npm test / npm run build；
   `test: null` 是 G5 合法形态，verdict_pass 的 G_command 整道为空）
3. **接入**：`pi install -l <本仓库绝对路径>`（如 `pi install -l 本仓库(work-flow-remake)`）。
   不装则窗口是裸会话：无角色注入、无 send_task 工具，arch 会自己干 dev 的活
   （2026-08-22 实测踩过）——扩展开销经 `pi.extensions` 从包根加载，装完用
   `WF_ROLE=arch pi --print "你是谁"` 自报身份验证
4. 三个窗口（或 `launch/trio.ps1 -Root <路径>`）：arch / dev / tester
5. arch 分发 M1（造 src/hello.txt）——**body 里明确写剧本**：第一版 hello.txt 内容
   故意写 not yet、不含 ok（LLM 忠于 plan 断言，不写进指令它不会故意做错，2026-08-22 实测）
6. dev 第一版：src/hello.txt 内容**故意不含 ok**（如写 "not yet"），[auto] 断言不满足；
   `wf/dev-output-M1.md` 两条断言编号**齐全**（不能漏编号——G_artifact_dev 会 block，
   review_request 发不出去，FAIL 流转走不起来；弱匹配只查编号、不查内容对错）→ 发 review_request
7. tester 跑断言发现 hello.txt 内容不含 ok → 写 `wf/test-report-M1.md`
   （判定：FAIL + 问题 M1-001 定位 hello.txt 内容）→ 发 fix_request
   —— **fix_request 的 artifact 填 tester 自己的报告路径 `wf/test-report-M1.md`**：
   G_artifact_report 查判定行；传 dev 产出会被拦（dev 产出无判定行是正常的——
   判定不是 dev 的权力，D-01；2026-08-22 实测传错过）
   —— **fix_request 通道必须真走一遍**：它是 M6-003 断过的通道（schema 拒 artifact），且 plan.md 目标定义的成功 = 完整流转（分发 → 开发 → FAIL → 修 → PASS → 人工放行）
8. dev 修复：hello.txt 内容改成含 ok → 重发 review_request
9. tester 跑断言全过 → 写 `wf/test-report-M1.md`（判定：PASS + 每条断言一行）→ 发 verdict_pass
   （questions 填 [human] 断言原文：文件内容读起来是句人话，不是占位符）
10. 人答 [human] 断言 → milestone_passed 回 arch
11. 验证：消息落点、state.json（round/失败计数走 FAIL→修）、wf/ 记录、/status 四行

### 判据

1. 每个窗口收到该收到的 type（无「窗口开了但不处理」的静默故障）
2. state.json 里程碑/轮次/失败计数按流程变化
3. 全程真 pi 进程（事件循环、sendUserMessage 语义），不是 mock
4. agent_end 提醒一轮即止：步骤 4–9 各窗口若收到「wf: 本轮结束」提醒，该回合结束后不再收到第二条、无窗口卡死
   （A9c 死循环修复的人工观测点——循环若仍在，第一轮 agent_end 后窗口即卡死，M6.6 跑不完；
   此判据与断言二互为充分必要，故不设单独凭证。arch 判定 2026-08-22）

### 判定

判定：PASS（第二轮重跑，2026-08-23，自动成环验证成功）。
