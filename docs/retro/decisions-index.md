## 一级决策（决定形状，五元组展开）

### D1：重组而非重写

- **问题**：前身 `work-flow` 能跑但自检 1995 行 > 运行时 1898 行，文档与实现不符，无版本控制。
- **选项**：① 继续在老仓库改；② 完全重写；③ 重组——事故换来的实现逐字照抄，自证机制大幅削减。
- **判据**：哪些代码是"事故换来的"（轮询兜底、条件清空、原子写），哪些是"自证长出来的"（六份契约、版本归档、合规检查器、约定台账）。
- **选择**：③。判据逐项写进 `docs/inherited/reuse.md`，实现前先查清单。
- **事后验证**：照抄的部分零返工；砍掉的自证机制无一被要求恢复。**但比值反而涨到 2.24**（见 D-41 序列）——削减的是老仓库的自证，长出来的是新形态的自证。

### D2：断言逐条签字，[auto]/[human] 二分

- **问题**：老仓库四个里程碑全部通过、零缺陷被人工关卡抓到，而 tester 规约明文要求的检查项 0/4 被执行。
- **选项**：① 验收标准写在规约里（老仓库做法）；② 写成可解析的断言 + 人逐条签字。
- **判据**：验收标准必须是"实现无法迁就的源"——所以它得在实现之前定，且由人确认。
- **选择**：②。6 条 `[human]` 逐条过人（`05276f0`），`[auto]` 须含命令或路径。
- **事后验证**：M6.6 的 FAIL 正是靠一条 `[human]` 断言抓到的——**auto 全绿而 human 判 FAIL**，这是整个设计最强的一次自证。

### D3：D-07 pi 只作参数进来

- **问题**：三个角色同进程加载时，模块级可变状态会共享同一份，e2e 整条路不成立。
- **选项**：① 模块内持有 pi/ctx（自然写法）；② 一路参数传递，只 `import type`。
- **判据**：不是可测试性这种空话——"某一层没法在同进程里驱动"的真实形态就是模块级状态。
- **选择**：②，落点 A9（grep 值导入 + 同进程三次 wire 验 root 互不相同）。
- **事后验证**：A9 全绿，e2e 得以在同进程驱动三个适配器。**但 A9 没能抓到 M6.6 的真问题**（接线缺失不是隔离问题）。

### D4：PASS / FAIL 拆成两个 type

- **问题**：老仓库 `verdict` 一个 type 两个目标地址（PASS→human、FAIL→dev），路由只能在代码里 if 分流。
- **选项**：① 沿用 `verdict` + 参数；② 拆成 `verdict_pass` / `fix_request`。
- **判据**：一个 type 两个方向 → 分流逻辑进代码 → 那正是老仓库 `ticket_result` bug 的栖息地（七处声明、零处工作）。
- **选择**：②。`to` 由表决定，发错地址在类型层无从表达。
- **事后验证**：9 条路由零方向缺陷。**读 `ROUTES` 只看到九条并列，看不出为什么不合并**——所以这条进了 `decisions.md`。

### D5：角色规约不走 pi skill 机制

- **问题**：需要给三个窗口注入不同的角色规约。
- **选项**：① 三份 `SKILL.md`（老仓库做法，也是 pi 官方分发形态）；② 扩展按 `WF_ROLE` 读一份 md 注入 system prompt。
- **判据**：三个理由叠加——skill 是渐进披露（规约必须常驻）；三份 skill 在三窗口都可发现（dev 看得见 tester 的规约，D-01 隔离失效）；老仓库 `--skill` 路径与目录名两处必须字符级一致，差三字母导致静默失活。
- **选择**：②。**第②条是决定性的**：不是"skill 不好用"，是语义不匹配（D-31 要求优先用成熟方案，这里是有理由的例外）。
- **事后验证**：P1 定案时发现自检未挂运行时（`specPresent` 无调用点）——**注入机制对了，但"验证注入还在"的机制漏了**，M6 修复轮补上。

### D6：进度改生成物

- **问题**：进度同时手写在 README、modules 散文、modules 表三处，全部过时且互不一致（三处写过 19/23/78，没一处对得上实测）。
- **选项**：① 人工同步三处；② 单点手写 + 其余只链；③ 从 plan.md + 实测计数生成。
- **判据**：D-04（一概念一权威）+ D-02（没有机制就不会同步）的合并症状；D-03（可推导的值不让人填）。
- **选择**：③（`ce52bc4`）。
- **事后验证**：**生成脚本自己出了静默 bug**——第一版自写正则没归一 CRLF，`autocrlf` 改行尾那天静默产出"0 个里程碑"并把整张表写空，无异常无非零退码（`58d0c12` 修复 + L10 钉住）。**生成物解决了分裂，引入了新的静默面。**

## 决策序列：D-41 的十一次审

这是全项目**最值得单独写一节**的东西——一条纪律与它自己的机制拉锯十一轮。

| 审次 | 日期 | 红线 | 结论 |
|---|---|---|---|
| 1 | 08-20 | 1.71 | 结构性产物，阈值留 1.0 不上调 |
| 2 | 08-21 | 1.95 | 构成 diff 写进文件头；**记下 L7 偏大的负债** |
| 3 | 08-21 | 2.09 | 无仪式成分；**L7 负债推迟到"下个里程碑开工前"** |
| 4 | 08-21 | 2.28 | M6 收尾 |
| 5 | 08-21 | 2.19 | M6 收尾后 |
| 6–8 | 08-22 | 2.22 / 2.21 / 2.22 | 逐轮增量构成 diff |
| 9 | 08-22 | 2.25 | A9c 修复轮 |
| 10 | 08-22 | 2.25 | **推翻第九次审的结论**：用例③的 mock 形态错了，"真实行为"的判断建立在错误 mock 上 |
| 11 | 08-23 | 2.24 | M6-010 唤醒链路接线 |

三个可写的点：

1. **红线永久红、永不 exit(1)**。设计时的理由是"做成硬失败会逼人改数字"，结果是一条从第一次运行起就红、审了十一次、阈值一次没动的线。它到底是仪表还是仪式？
2. **负债推迟的自我实现**。第二次审记下"L7 偏大"，第三次审写"下次红了先看它"，结果它从 182 行长到 236 行——**推迟的措辞本身制造了推迟**。第三次审改口为"升级为下个里程碑开工前第一件事"才真的还掉（`3fe16f6`）。
3. **第十次审推翻第九次审**。同一个判据（真实行为 vs 仪式）在错误的 mock 形态上给出了错误结论。**审计机制自己需要被审计**——这是元机制递归的实证。

## 三个决策失败（文章的核心素材）

### F1：宣布"一个提交一件事"的提交，自己违反了它

`42bd0e7` 的 message 是"纪律 +1：D-45 一个提交一件事"——**而这个提交把 D-44 整行替换成了 D-45**，违反的是 `disciplines.md` 自己表头第三条（只增不改）。两个提交无人发现，直到后来补 D-47 + 检查器（`8b64469`/`74dedca`）才被抓出来，并在 `ALLOWED_DELETIONS` 里记为历史事故。

**可写的点**：纪律的宣布行为本身不受纪律约束——这是"纪律不进拦截链就不会被遵守"（D-02）的最讽刺形态，而它发生在 D-02 已经写下之后。

### F2：M6.6 判 FAIL——mock 全绿，真实链路从未接线

真开三窗口跑（临时空项目）判 **FAIL**：

- 每个环节都要人往窗口手动注入指令才动，**没有任何一环是自动的**
- tester 对 round 2 的 `review_request` 延迟 **47 分钟**（10s 轮询早该处理）
- 根因：`watchInbox` 在 `src/adapter/` **零调用**，`git log -S` 证明**从未接线过**（不是回归删除）
- `status.ts` 注释写着"wire 的 session_start / watchInbox 共用同一份"——**设计写了，实现没做，且无机制抓**

**可写的点**：这是 D-02 最精确的形态（写了但没接线），也是 289 个用例、11 次审计、7 层架构全部没能抓到的东西。抓到它的是**一条人写的 `[human]` 断言**——规划书风险节甚至预告过这个形状（"mock-pi 验的是接线正确，不验 pi 真实行为"）。**预告了、还是漏了**：知道边界存在，不等于在边界上放了哨兵。

### F3：tester 真实流程验出三个 mock 测不到的 bug

- `schema` 缺 `artifact` 字段 → tester **无法投递**（E1 直调 execute 绕过 schema 校验，所以测试绿、真窗口炸）
- P1 自检 `specPresent` 无调用点 → 注入被替换时无告警（R5 头注释承诺"M6 挂 agent_start"，wire 只挂了四个钩子）
- `agent_end` 提醒 `followUp` 死循环（且第一版修复的 mock 形态错了，两轮才对）

**可写的点**：三个都在"mock 与真实的缝"上。这条缝在规划书里被明确标注为已知风险，但**没有任何机制守它**——守它的只能是真实运行。

「一条也不新增 gate 脚本」是自欺，已按评审修正为诚实标注。

### N1 断言署名（src:ai / src:human）

- **提案**：每条断言标来源——AI 起草 = `src:ai`，人逐条确认后改 `src:human`。D-21「接受稀释」升级成可查机制：签字从自述变 git 痕迹。
- **评审修正**：「一条也不新增 gate 脚本」**是自欺**——署名要解析器加语法 + 一条 block 判据，可失败性要 G_plan 查红场景行，这就是**两条新判据**。量小不等于不存在；诚实标注比声明「零新增」更符合本项目风格（D-02 的形状就是「写了但没落点」）。
- **落点**：签字轮（D-24 逐条过人）。

### N2 垂直切片 / walking skeleton

- **提案**：横切（01→02→…→07）把跨层缺陷排到最后一天才暴露——M6.6 FAIL 的根因（`watchInbox` 从未接线）正是跨层缺陷。
- **评审修正**：诊断成立，辩护（重组非探索、单层可照抄）也成立——但辩护到 `wire.ts` 断了：老仓库经验覆盖照抄部分，**接线是唯一新写且最贵的一层**。walking skeleton 是正确折中。这条是给下一个项目的规划书检查，本仓库已验收，别试图回改（D-14）。
- **落点**：里程碑规划轮（arch 写里程碑时）。

### N3 断言可失败性（红场景）

- **提案**：每条断言必须写红场景——什么条件下它真的会红。`d10d1eb` 教训：全验收后 `some(!passed)` 不可满足 → 真空绿。
- **评审修正**：**空话风险**——红场景写成「断言不满足时红」这种废话过不了检查。必须含具体物证（文件名/命令/条件）。套 D-25 的措辞：**红场景里必须出现路径或命令**，否则它就是新的仪式。
- **落点**：起草轮（AI 写断言时）。

### N4 术语表

- **提案**：项目术语独立落盘，防「收缩三义」这类实测事故（本对话里就发生过一次往返澄清）。
- **评审修正**：该独立存在（反驳成立）。三节结构 + 零误报 grep（拼写一致）是对的；「已判定的歧义」节与 disciplines 每条带来源同哲学。时机对：M6 已验收 =「M6 后」。
- **落点**：澄清全程，签字轮一并过。
